Latency percentiles (tail behavior)

p50 / p90 / p95 / p99 of sustained (model-only) latency, log scale. A steep climb from p50 to p99 means occasional slow frames — worth knowing before trusting a single "avg FPS" number.

Per-frame sustained latency (stability over the run)

Model-only latency for each of the 100 sampled frames, in run order — this is what a continuous pipeline actually experiences per frame. Each format has its own y-scale.

Per-call benchmark-loop overhead (not present in production)

Extra wall-clock time on top of the model's own latency, from calling Ultralytics' .predict() once per image in this benchmark's loop (dataloader/argument setup re-run each call). It's ~72 ms on average and spikes periodically (every ~10 frames) to 350–400+ ms — consistently, regardless of format (pt/onnx/engine all show near-identical overhead), which is exactly what you'd expect from a Python-level artifact rather than a GPU or model effect. A persistent streaming loop like hydrakon_bringup's never pays this per frame — it's shown here only to explain why this benchmark's naive wall-clock FPS looks much lower than what you see in the running car.

Accuracy — official Ultralytics benchmark() validation

mAP50-95 and speed from Ultralytics' own export+val() pipeline (100-image subset, conf=0.001 — the validation-standard threshold, stricter than predict()'s default 0.25, which is why these inference times run higher than the sustained-latency numbers above). The point of this table: accuracy barely moves between formats — TensorRT's FP16 quantization costs ~0.001 mAP for ~2.6× the throughput.
